### Root Cause Hypothesis
The AL compiler uses a specific text encoding (likely Windows-1252 / ANSI) when reading AL source files. If the actual bytes of the glapproval files contain characters that look IDENTICAL to ASCII in UTF-8 but DIFFER when interpreted as Windows-1252, this would cause the compiler to see different characters than what Format-Hex shows.

The file appears clean as UTF-8 bytes, but the AL compiler processes them through a different code page that shifts character values, causing the parser to see non-quote characters where `"` should be.

### Definitive Test
Inside custcontacts container (which successfully compiles custcontacts), run:

The bytes must match what we saw from GSPRO. If they do, the fix is to re-encode ALL .al files to UTF-8 with BOM.

### THE FIX
On GSPRO, re-encode ALL 8 GLApproval .al files from their current encoding to UTF-8 with BOM, with CRLF line endings:
```powershell
$files = Get-ChildItem "C:\ProgramData\BcContainerHelper\Extensions\glapproval\my\GLAccApproval\src" -Recurse -Include *.al
foreach ($f in $files) {
    $content = [System.IO.File]::ReadAllText($f.FullName)
    [System.IO.File]::WriteAllText($f.FullName, $content, [System.Text.Encoding]::UTF8)
}
```
This forces re-encoding. Then recompile.

### Most Likely Root Cause
The AL compiler (16.4.33.4744) uses Windows-1252 (code page 1252) by DEFAULT when reading source files, NOT UTF-8. Characters 0x80-0x9F are interpreted differently:
- Byte 0x93 (curly open quote in Windows-1252) = " in UTF-8 would be E2 80 9C
- BUT if the original file was encoded as Windows-1252 and then saved as UTF-8, a " encoded as 0x93 in Win-1252 would appear as a single byte 0x93 which is INVALID UTF-8

However, Format-Hex showed clean bytes. Could be that the SOURCE of the files (where they were originally created) used Windows-1252 encoding, and when they were converted to UTF-8, some characters got corrupted.
